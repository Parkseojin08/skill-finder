# Skill Finder 성능 토론 최종 보고 (진행자, 2026-10-30)

주제는 두 가지였습니다. (1) 검색 속도와 정확도, (2) 메모리·캐시 등 앱 전체 최적화.
- 패널 3명이 2라운드씩 썼습니다. p1은 검색·랭킹, p2는 성능·시스템, p3는 런타임·메모리를 맡았습니다.
- 진행자는 1·2라운드의 핵심 숫자를 직접 다시 재거나 다시 채점했습니다.
- 프로젝트 파일, 4317 앱, `data/`는 건드리지 않았습니다. 모든 측정은 DB 사본으로 했습니다.

**네트워크 사용**
| 누구 | 쓴 것 |
|---|---|
| 진행자 | 실제 검색 0회 |
| p1 | GitHub 0회, skills.sh API 40회 |
| p2 | 실제 검색 28회(그중 10회는 실수로 토큰 없이) |
| p3 | 실제 검색 0회, git 부분 fetch 24회(API 한도를 쓰지 않음) |

**용어**
- p50: 중앙값. p90: 느린 쪽 10%가 시작되는 값.
- nDCG@10: 상위 10개의 순서 품질. 0~1이고 높을수록 좋습니다.
- must-find: 반드시 상위 N 안에 나와야 하는 정답이 실제로 나온 수. 판정자와 무관하게 미리 정한 지표입니다.
- CI: 95% 신뢰구간. "하한 > 0"이면 우연이 아닌 개선으로 봅니다.
- 재생: 실제 검색 때 녹화한 네트워크 응답을 그대로 다시 돌려주는 측정. 실제 검색 없이 같은 조건으로 비교할 수 있습니다.
- mmap: SQLite가 DB 파일을 메모리에 매핑해 바로 읽는 방식.
- 전용 메모리: 이 프로세스만 쓰는 메모리. 작업 관리자의 기본 "메모리" 열에 가깝습니다.

## 한 줄 요약

- **검색 속도**: 가장 큰 변화는 "없음" 판정을 하루 동안 기억하는 부정 캐시입니다.
  - 앱을 다시 켠 뒤 같은 검색을 하면 p50이 **약 2.0초에서 0.07초**로 줄어듭니다(토큰 없음, 녹화 재생, 진행자 재현, 결과 10/10 같음).
  - 토큰이 있으면 **0.83초에서 0.46초**입니다(근사값).
  - 처음 하는 검색의 p50 2.41초는 거의 그대로입니다. 이 시간은 GitHub 응답을 차례로 기다리는 시간이라, 이번 안들로는 줄지 않습니다.
  - 엔진 CPU 정리는 검색당 13~15ms라 사람이 느끼지 못합니다.
- **정확도**: 영어 파일 형식·약어 별칭 8개를 넣으면, 별칭 단어가 든 새 질의 14개에서 nDCG@10이 **0.601에서 0.783**(+0.182, CI [0.087, 0.288])으로 오릅니다.
  - 별칭 예: ppt→pptx, excel→xlsx, "word 문서"→docx, k8s→kubernetes, postgres→postgresql.
  - 공식 스킬 must-find는 **1/6에서 6/6**이 되고, 나빠진 질의는 0개입니다.
  - 다만 정렬 규칙을 바꾸는 일이라 **사용자 결정**이 필요합니다. 별칭이 작동하는 질의는 지금까지 나온 질의의 약 6%입니다.
- **메모리**: 트리 캐시에 크기 상한이 없습니다.
  - 인기 저장소를 강제 수집하면 **157MB**가 앱을 끌 때까지 남습니다. 대기 중 앱 전체가 약 110MB이니 그보다 큽니다.
  - 검색 12회 뒤에는 96MB가 10분 동안 남습니다.
  - 항목 수 상한을 두면 각각 약 9MB, 46MB 이하로 묶입니다.
  - SQLite mmap은 전용 메모리를 거의 늘리지 않으면서(+0~5MB) 로컬 SQL을 14ms에서 7ms로 줄입니다.
- **첫 화면**: 첫 카드 5개 중 최종 결과까지 남는 것은 평균 **3.75개**입니다(12개 질의 중 8개는 4개 이상).
  - 지난 로드맵의 기준(4.5 미만이면 화면 안정화)을 충족합니다.
  - 6줄 수정으로, 순서가 뒤집히는 질의 3개의 안정 시점이 0.26~0.97초 당겨집니다.
