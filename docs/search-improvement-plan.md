# 검색 엔진 개선 진행안 (2026-10-28)

에이전트 4명(실측 분석가·파이프라인 설계자·관련도 연구자·사용자 관점 비평가)이 따로 조사하고, 서로의 제안을 놓고 한 번 더 토론한 결과를 정리했어요. 아직 코드는 바꾸지 않았어요.

## 지금 문제 (측정값)

15개 검색어를 실제 DB 사본으로 측정했어요.

- **속도**
  - 검색 한 번에 3.3~11.3초 걸려요.
  - 단계별 비중은 후보 수집 51%, SKILL.md 확인 39%, 별 수 확인 10%예요.
  - 후보 수집에서는 GitHub 코드 검색이 가장 느려요(평균 2.36초).
- **놓치는 결과**
  - 상위 60개로 자르기(`pipeline.ts:406`)가 별 5천 필터(`pipeline.ts:474-482`)보다 먼저 돌아요.
  - 그래서 60개 자리를 어차피 버려질 저별 후보가 차지해요.
  - 대표 사례: anthropics `pdf`(설치 21.7만)가 FTS 51위라 잘려요.
  - 결과적으로 숨김이 78%이고, 놓친 결과가 63개예요.
- **엉뚱한 결과**
  - 상위 10개 중 약 32%가 무관해요.
  - 원인 1: 단어가 하나도 안 맞는 외부 결과. skills.sh가 의미 검색이라 이런 결과가 들어와요.
  - 원인 2: 흔한 단어 하나만 맞은 결과.
  - 원인 3: 설치 수가 없는 스킬(전체의 96.7%)이 저장소 별 순으로 정렬돼, 별이 많은 거대 저장소가 위를 차지해요.
- **한국어 버그**
  - `matchTokens`(`rank.ts:76`)가 `pdf에서`를 한 단어로 봐요.
  - 그래서 FTS로는 찾아도 관련도 단어 일치가 0이 돼요.
- **느린 DB 조회**
  - `store.ts:271`, `store.ts:392`의 `COLLATE NOCASE` 조회는 인덱스를 못 타서 전체를 훑어요.
  - 호출당 30~40ms이고, 인덱스를 타면 0.2ms예요(약 150배).

### 갈렸던 쟁점과 결론

- **별 수를 모르는 저장소를 어떻게 할지**
  - 결론: 색인된 후보는 DB에 있는 별 수를 그대로 써요. 7일 넘게 오래된 값은 0개이고, 5천 경계 근처 저장소도 약 90개뿐이에요.
  - 경계 완충: 4천~5천인 후보는 앞에서 버리지 않고 마지막 판정에 맡겨요.
  - 처음 보는 저장소는 SKILL.md를 읽기 전에 `getRepoMeta`(24시간 캐시)로 별 수부터 확인해요. 5천 미만이면 읽지 않아요.
  - 마지막 판정 규칙은 지금과 같아요. 별 수를 모르면 숨겨요(DECISIONS "모르면 숨김").
- **백그라운드 별 갱신**: 설계자는 필요하다고 했어요. 실측상 값이 충분히 최신이라 **나중으로** 미뤄요.
- **R≥0.5 등급**: R은 검색마다 다시 맞춘 상대값이라 기준으로 쓰기 어려워요. 실제로 무관 사례 3개 중 2개를 통과시켰어요. **버려요.**
- **collectRepos가 병목인지**: 한 단어 검색에만 해당해요. 측정한 사례에서는 2초 안팎이었어요. 2단계에서 첫 결과 앞당기기와 같이 처리해요.
- **일치 0 제외만으로 충분한지**: 엉뚱한 결과의 약 43%만 줄어요. 나머지는 정렬 문제라 3단계(사용자 확인)에서 다뤄요.

## 진행안

### 1단계: 바로 하기 (사용자 결정과 충돌 없음)

1. **NOCASE 인덱스**
   - `repo`와 `full_name`에 `COLLATE NOCASE` 인덱스를 추가해요(`db/schema.ts` 마이그레이션).
   - 효과: 검색당 최대 약 1초 단축.
2. **`matchTokens` 수정**
   - 한글 단어에 붙은 영어 조각을 따로 떼요. `ftsQuery`(`pipeline.ts:95`)와 같은 규칙이에요.
   - 접두 일치도 더해요. 예: `docker`↔`dockerfile`, `extract`↔`extraction`.
   - README 추천도 이 함수를 쓰므로 그쪽 테스트도 같이 확인해요.
3. **별 필터를 자르기 앞으로**
   - 위 결론대로 적용해요. 임시 결과(`pipeline.ts:398-401`)에도 같은 필터를 걸어, 떴다가 사라지는 카드를 없애요.
   - 효과: `extract tables from pdf` 후보가 7개에서 28개로 늘어요. 저별 후보의 SKILL.md 읽기도 줄어 확인 단계가 짧아져요.

**1단계 결과 (2026-10-28 완료).** 18개 검색어로 `server/scripts/measure-search.ts`를 돌려 전후를 비교했어요.
- 결과 수: 18개 중 17개 검색어에서 늘었어요(합계 281 → 456).
  - 예: `extract tables from pdf` 5 → 29개, anthropics pdf 빠짐 → 1위.
  - 줄어든 곳: `commit message` 14 → 11개.
- 전체 시간: 109.5초 → 89.2초.
- 한국어: `pdf에서 표 추출`의 상위 10개 평균 R이 0.253 → 0.562로 올랐어요.
- 숨김 개수: "별 5천 미만 숨김"이 커졌어요. 이제 상위 60개가 아니라 후보 전체를 세기 때문이에요(DECISIONS 기록).
- 저장된 별 수가 7일보다 오래되면 미리 빼지 않고 다시 확인해요.
- 별 적은 복사본(포크)은 숨김 개수에 넣지 않고, 다운로드를 원본에 더해요.

### 2단계: 이어서 하기 (사용자 결정과 충돌 없음)

4. **첫 결과 앞당기기**
   - 로컬 FTS 결과(0.24초)를 먼저 보내요. GitHub 결과는 들어오는 대로 처리하고, collectRepos는 따로 이벤트로 보내요.
   - 소스별 진행 상태 이벤트(`{type:'source', …}`)와 경과 시간을 화면에 보여 줘요.
5. **FTS를 AND로 먼저 찾고 모자라면 OR로 채우기**
   - 지금 `ftsQuery`(`pipeline.ts:98`)는 OR만 써요.
   - 바뀌는 것은 후보 집합뿐이고 정렬은 그대로라 결정과 충돌하지 않아요.

**2단계 결과 (2026-10-28 완료).** 1단계 결과와 같은 18개 검색어로 비교했어요.
- 첫 카드까지: 검색당 평균 1.4초 → 0.2초(합계 25.0초 → 4.0초).
- 전체 시간: 89.2초 → 60.7초.
- 결과 수: 대부분 늘었어요(합계 456 → 541).
- 한 단어 검색(`rea`, `security`)은 최종 결과가 2.7 → 6.2초, 4.4 → 7.1초로 늦어졌어요.
  - 최종 결과가 같은 이름 저장소 검색과 새 저장소 읽기를 끝까지 기다리기 때문이에요(최대 약 14초).
  - **정정(2026-10-28 검색 토론):** 위 원인 설명은 틀렸어요.
    - 진짜 원인: 측정이 질의를 쉬지 않고 연달아 보내서 GitHub 코드 검색 TokenBucket(분당 9회) 대기와 한도 초과(403)에 걸렸어요. 같은 이름 저장소 검색 자체는 1.1~1.7초예요.
    - 질의 사이를 7초 띄우고 같은 코드를 다시 재면 18개 질의 합계가 81.7초에서 49.0초로, p90이 7.1초에서 3.3초로 줄어요.
    - 그래서 이 문서의 2·3단계 속도 수치는 측정 잡음이 섞인 값이에요.
    - 자세한 내용은 `docs/search-debate-final-report.md`에 있어요.
  - 첫 카드는 0.05초 안팎에 떠요.
  - 1단계 측정 때는 이 검색이 수집 단계 안에서 빨리 끝났던 것으로 보여요. 네트워크에 따라 달라져요.
- GitHub 코드 검색이 4초를 넘기면 그 검색은 60초만 캐시해요.

### 3단계: 사용자 확인이 필요한 것

**2026-10-28 사용자 결정: A~E 모두 아래 안대로 진행했고, 같은 날 구현을 마쳤어요.** 구현하면서 정한 세부는 DECISIONS에 적었어요.

**3단계 결과.** 2단계 결과와 같은 18개 검색어로 비교했어요.
- 상위 10개의 관련도 0.4 미만 결과: 합계 41개 → 20개(처음에 31 → 20으로 잘못 적었다가 바로잡음).
  - 이 지표는 시스템이 스스로 매긴 R이에요. 그런데 A가 숨기는 결과는 정의상 R이 0.4 미만이라, 줄어드는 것이 당연해요. 정확도의 증거로는 약해요(검색 토론 패널 10번 지적). 사람이 판정한 정답셋으로 다시 재야 해요.
- 엉뚱한 결과가 많던 검색어

  - `rea`: 6 → 1개. 무관한 hyperframes 등 14개가 빠지고 morluto/rea 스킬 5개만 남았어요. reverse-engineer-anything은 1위 그대로예요.
- 시간: 첫 카드 4.0초 → 4.3초(18개 합계), 전체 60.7초 → 60.7초. 차이는 네트워크 변동 범위예요.
- 사용자께 보여 드린 예시

### 하지 않기로 한 것
