# 업데이트 서명 키: 백업·분실·교체 절차

Windows 배포판의 자동 업데이트는 서명을 확인한 뒤에만 설치합니다(D#f1ce). 이 문서는 그 키를 잃었거나 새어 나갔을 때 무엇을 하는지 정리합니다(기능 제안서 P12, 결정 21).

## 1. 지금 구조

| 무엇 | 어디 |
|---|---|
| 비공개 키 (RSA 3072, PKCS#8 PEM) | 배포하는 PC의 `%USERPROFILE%\.skill-finder-release\update-signing-key.pem`. 저장소·zip·사이트에는 없음 |
| 공개 키 (앱) | `server/src/release.ts`의 `UPDATE_PUBLIC_KEY` |
| 공개 키 (실행기) | `launcher/SkillFinder.cs`의 `UpdateKeyModulus` / `UpdateKeyExponent` |
| 서명하는 곳 | `npm run package`(`scripts/package-win.mjs` "서명" 단계): `meta.json`의 `signature`(버전·크기·SHA-256)와 `notesSignature`(변경 기록) |
| 확인하는 곳 | 실행기 `VerifyRelease`(지금 설치된 실행기가 다음 버전을 확인), 앱 `update.ts`("새 버전" 표시와 변경 기록) |

- 업데이트를 확인하는 것은 **지금 설치된 실행기**입니다. 그래서 키를 바꾸려면 새 키를 믿는 실행기를 옛 키로 서명해 먼저 내보내야 합니다.
- 실행기와 앱은 키를 **하나만** 믿습니다. 지금은 두 키를 함께 믿는 코드가 없습니다.
- npm 패키지(`npx @seojin08/skill-finder`)는 이 키를 쓰지 않습니다. npm 계정(2단계 인증)이 지킵니다.
- 서명 문구에 날짜가 없습니다. 사이트가 새 버전을 숨기고 옛 버전을 계속 보여 주면(freeze) 알 수 없습니다. 더 낮은 버전으로 내리는 것은 막혀 있습니다(D#6535). 날짜가 든 서명은 다음에 실행기를 바꿀 때 v1 서명 옆에 더합니다(결정 21).

## 2. 백업 (지금 한 번, 키를 바꿀 때마다)

1. `update-signing-key.pem`을 오프라인 저장소 두 곳에 복사합니다. 예: 암호화한 USB, 비밀번호 관리자의 보안 메모.
2. 클라우드 동기화 폴더, git 저장소, 메신저에는 두지 않습니다.
3. 백업본이 맞는지 확인합니다. 백업본 경로를 지정해 공개 키를 출력하고, `release.ts`의 키와 같은지 봅니다.
   - PowerShell: `$env:SKILL_FINDER_SIGNING_KEY='<백업본 경로>'; node scripts/signing-key.mjs`

## 3. 키를 잃었을 때 (비공개 키가 없음)

설치된 앱은 새 업데이트를 받을 수 없습니다. 새 키로 서명한 버전은 실행기가 거부하고, 앱도 "새 버전"을 보여 주지 않습니다.

1. `node scripts/signing-key.mjs`로 새 키를 만듭니다. 옛 파일이 있으면 아무것도 하지 않으니, 옛 파일을 먼저 다른 이름으로 옮깁니다.
2. 출력된 공개 키를 `server/src/release.ts`와 `launcher/SkillFinder.cs`에 넣고 버전을 올려 `npm run package`로 배포합니다.
3. 소개 페이지 첫 화면에 안내합니다. "업데이트 서명 키가 바뀌었습니다. 이 페이지에서 새로 내려받아 다시 설치하세요. 설정과 즐겨찾기는 데이터 폴더에 남습니다."
4. 기존 설치는 실행기가 "서명이 맞지 않아 설치하지 않습니다"를 띄우고 지금 버전으로 켜집니다. 망가지지는 않습니다.
5. `docs/DECISIONS.md`에 날짜와 이유를 한 줄 남기고, 2절대로 새 키를 백업합니다.

## 4. 키가 새어 나갔을 때 (다른 사람이 가졌을 수 있음)

가짜 업데이트를 퍼뜨리려면 키와 함께 **업데이트 주소를 차지해야** 합니다. 업데이트 주소는 Cloudflare Pages `seojin-skill-finder`와 옛 Worker `skill-finder`입니다. 그래서 둘 다 막습니다.

1. Cloudflare 계정 비밀번호와 2단계 인증을 확인합니다. wrangler·API 토큰을 폐기하고 다시 발급합니다(`npx wrangler@4 logout` 후 로그인).
2. 옛 키가 아직 있으면 5절의 "교체"를 **바로** 합니다. 이때 전환 버전의 실행기는 새 키 **하나만** 믿게 합니다. 옛 키를 함께 믿는 기간을 두지 않습니다.
3. 옛 키가 없으면(새어 나가고 잃기도 함) 3절대로 합니다.
4. 소개 페이지와 GitHub README에 날짜, 영향 범위, 다시 설치 안내를 남깁니다.

## 5. 계획한 교체 (옛 키가 있을 때)

1. 새 키를 만듭니다. 옛 파일과 다른 경로를 `SKILL_FINDER_SIGNING_KEY`로 지정해 `node scripts/signing-key.mjs`를 실행합니다.
2. **전환 버전 N**을 만듭니다.
   - 실행기와 앱이 두 키 중 어느 것으로 서명돼도 받아들이게 고칩니다(공개 키 목록). 새어 나간 경우에는 새 키만 믿게 합니다.
   - 서명은 **옛 키**로 합니다. 지금 설치된 실행기는 옛 키만 믿기 때문입니다.
3. N이 충분히 퍼질 때까지 기다립니다. 보통 몇 주이며, 사이트 내려받기 수로 가늠합니다.
4. **N+1부터 새 키로 서명합니다.** N보다 오래된 설치는 3절처럼 다시 설치해야 합니다.
5. 다음 실행기 변경 때 공개 키 목록에서 옛 키를 뺍니다.
6. 새 키를 2절대로 백업하고, 옛 키는 지웁니다. 키가 새어 나간 경우가 아니면 기록용으로 오프라인에 보관해도 됩니다.

## 6. 시험

- 실행기 시험(`scripts/test-launcher.mjs`, `npm run package`에 포함)은 `SKILL_FINDER_UPDATE_KEY`로 **127.0.0.1 업데이트 페이지에만** 시험 키를 씁니다. 실제 키를 시험에 쓰지 않습니다.
- 키를 바꾼 뒤에는 `npm run package`가 서명 직후 `release.ts`의 공개 키로 다시 확인합니다. 공개 키를 넣지 않았으면 "서명 키가 server/src/release.ts의 공개 키와 맞지 않습니다"로 멈춥니다.
